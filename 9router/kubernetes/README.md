# ☸️ 9Router + Hermes on Kubernetes

The [Compose stack](../docker-compose/) as Kubernetes manifests, with
[`generate.sh`](generate.sh) handling every secret. Verified end to end on OrbStack
(`v1.35.6+orb1`).

| Object | Name | Notes |
|---|---|---|
| Namespace | `9router` | |
| StatefulSet + Service | `ninerouter` | 9Router, port 8080, 2Gi PVC |
| StatefulSet + Service | `hermes` | API 8642, dashboard 9119, 5Gi PVC |
| ConfigMap | `hermes-config` | seed `config.yaml`, generated by kustomize |
| Secret | `9router-secrets` | `INITIAL_PASSWORD`, `JWT_SECRET`, `API_KEY_SECRET`, `MACHINE_ID_SALT` |
| Secret | `hermes-secrets` | dashboard hash + session secret, `API_SERVER_KEY`, `OPENAI_API_KEY` |

> ⚠️ **The Service is `ninerouter`, not `9router`.** Service names are DNS-1035 labels, which must start
> with a *letter* — `9router` is rejected outright by the API server. Namespaces and StatefulSets are
> DNS-1123 and accept a leading digit, which is why only the Service needed renaming. In-cluster the
> endpoint is therefore `http://ninerouter:8080/v1`.

## 🚀 Deploy

```bash
./generate.sh --up
```

One command: secrets, `kubectl apply -k .`, wait for 9Router, mint its API key, restart Hermes, warm the model
catalog, then verify the two can talk. It is also the repair command — re-run it any time. Deleting the PVCs
invalidates the API key (9Router regenerates its machine id and purges old keys), which otherwise shows up as
a healthy stack whose picker says **"9router · 1 models"**.

The steps individually:

```bash
./generate.sh
```

```bash
kubectl apply -k .
```

```bash
kubectl -n 9router rollout status statefulset/ninerouter
```

```bash
./generate.sh --key-only
```

That last step mints a 9Router API key from inside the pod, stores it in `hermes-secrets`, and restarts
Hermes. It is a separate step because 9Router has to be running before it can issue a key — a fresh install
has none at all.

Then reach either dashboard:

```bash
kubectl -n 9router port-forward svc/hermes 9119:9119
```

```bash
kubectl -n 9router port-forward svc/ninerouter 8080:8080
```

## 🔑 generate.sh

| Command | Does |
|---|---|
| `./generate.sh` | Creates the namespace, generates every secret, applies both Secrets, prints them |
| `./generate.sh --print` | Reads the Secrets back out of the cluster and prints them — generates nothing |
| `./generate.sh --key-only` | Mints/fetches the 9Router API key, patches `hermes-secrets`, restarts Hermes |
| `./generate.sh --rotate` | Forces new values for everything except `INITIAL_PASSWORD` — **invalidates every issued 9Router API key**, which the next run re-mints |

`NS=other-ns ./generate.sh` targets a different namespace; `HERMES_IMAGE=…` pins a different tag.

It needs `kubectl`, `openssl`, `envsubst` (`brew install gettext`) — **and a running container engine**, even
though the workload is in Kubernetes. That is because the dashboard password is hashed with scrypt by a helper
that only exists inside the Hermes image, so the script runs that image locally for one command. Hash with a
different tag than the StatefulSet runs and you may be verifying against a different build.

Every 9Router secret is deliberately *preserved* across re-runs rather than regenerated, because each one is
bound to the PVC:

- **`INITIAL_PASSWORD`** — applied only when 9Router initialises its PVC; rewriting it just makes the Secret
  disagree with the live database.
- **`MACHINE_ID_SALT`** — derives `/app/data/machine-id`. Change it and 9Router rewrites that file and
  **purges every API key bound to the old id**; issued keys disappear from its `apiKeys` table and start
  returning `401`.
- **`API_KEY_SECRET`** — the HMAC that signs issued keys; rotating it invalidates them the same way.
- **`JWT_SECRET`** — signs dashboard sessions; rotating it logs everyone out.
- **`OPENAI_API_KEY`** (the 9Router key) — so a plain `./generate.sh` does not orphan a working Hermes.

`--rotate` overrides all of that **except `INITIAL_PASSWORD`**, which is never rotated: 9Router reads it only
when initialising an empty PVC, so a new value would leave the Secret disagreeing with the live database —
locking you out of the dashboard *and* out of key minting, which logs in with it. A plain re-run then
re-mints the API key automatically. To actually change the 9Router password, re-initialise its PVC:

```bash
kubectl -n 9router delete statefulset ninerouter --cascade=foreground && kubectl -n 9router delete pvc data-ninerouter-0 && kubectl apply -k .
```

> 🔒 9Router locks out after a few failed logins (`Too many failed attempts. Try again in 30s`). Its own
> recovery path is **9Router CLI → Settings → Reset Password to Default**; deleting the PVC is the blunt
> alternative when the instance holds nothing you need.

> 🔎 **"9router · 1 models" in the picker means the key is dead, or discovery has never run.** Hermes falls
> back to the configured `default_model` alone rather than erroring. `./generate.sh --key-only` fixes both: it
> validates the stored key, re-mints if 9Router no longer accepts it, restarts Hermes and warms the catalog.

The plaintext dashboard password is kept in a separate `hermes-dashboard-login` Secret that is **not** mounted
into any pod — the pod only ever sees the scrypt hash. It exists so `--print` can show you the password and
`--key-only` can log in to warm the model catalog.

Everything else is fresh on every run, so re-running rotates the Hermes dashboard password, its session
secret and the API server key. Rotating the session secret invalidates live dashboard sessions.

The Hermes dashboard password is readable any time with `./generate.sh --print`.

## 🧩 Why the pieces are shaped this way

**The init container that seeds `config.yaml`.** Hermes rewrites its own config at runtime — the dashboard's
Config page saves to `/opt/data/config.yaml`. A ConfigMap mount is read-only, so mounting it directly makes
SAVE fail. `seed-config` copies the ConfigMap into the PVC on first start and leaves it alone thereafter, so
the file is writable and edits survive restarts. Change the seed for a *fresh* install; change a running one
through the dashboard, or delete the PVC.

**Both blocks in `config/config.yaml`.** `providers.9router` defines the endpoint;
`model.provider` binds the default chat to it. With `model` as a bare string the provider resolves empty and
Hermes silently falls back to its built-in Nous provider, failing every call with
`HTTP 401: Missing Authentication header` — an error that looks like a key problem but is not.

**Three secrets that gate startup, not just features:**

| Missing | Symptom |
|---|---|
| `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` | Hermes refuses to bind a non-loopback dashboard and crash-loops — `CrashLoopBackOff`, never Ready |
| `API_SERVER_KEY` | The API server never binds, with **no log line at all**; the readiness probe on `/health` fails forever |
| `OPENAI_API_KEY` | Pod is Ready, but every model call returns 9Router's `API key required for remote API access` |

**The 9Router readiness probe hits `/`, not `/v1/models`.** 9Router only trusts loopback *inside* the
container; a kubelet probe is never loopback, so the API path would 401 and the pod would never go Ready.

## 🔎 The model picker: what the counts mean

Hermes' **Switch Model** dialog does not surface routing errors — it silently falls back to whatever it can
resolve. The model *count* next to `9router` is therefore the real diagnostic:

| What you see | Cause | Fix |
|---|---|---|
| `9router · 1 models` | The API key is dead or missing. Hermes cannot list anything, so it shows only the configured `default_model`. | `./generate.sh --up` |
| `9router · N models`, but a model you just added in 9Router is missing (filter says *no models match*) | Stale catalog. Hermes discovers models on demand and caches them for ~1h, so anything added on the 9Router side afterwards is invisible. | **Refresh Models** in the dialog, or `./generate.sh --key-only` |
| `9router · 0 models` | 9Router is unreachable (wrong `base_url`, pod/container down). | Check the endpoint is up and the URL in [`config/config.yaml`](config/config.yaml) |

The two failure modes look alike but are unrelated: **1 model = auth**, **missing-a-few = cache**. Only the
first is a real fault; the second is expected any time you change 9Router's provider list.

### Adding models on the 9Router side

9Router's Providers page (e.g. **OpenCode Free → Add Model**) changes only 9Router. Hermes keeps serving its
cached list until refreshed, so the new ids will not appear in the picker or match its filter. Refresh after
adding, and confirm the count moved — for example 691 → 696 after adding four `oc/…` models.

List what 9Router actually serves, so you can compare against the picker:

```bash
kubectl -n 9router exec ninerouter-0 -- node -e "fetch('http://127.0.0.1:8080/v1/models').then(r=>r.json()).then(j=>console.log(j.data.length+' models'))"
```

### The current model changed on its own

The picker writes to `config.yaml` — the dialog says *"Saves to config.yaml"*. Switching a model in the UI
therefore overrides the default you set in the seed file, and it persists. If the badge shows something you
did not choose (for example `alicode-intl/qwen3.5-plus` when your default is `oc/mimo-v2.5-free`), switch it
back in the dialog; editing the seed file only affects a fresh install.

## ✅ Verify

Config landed in the PVC and is writable:

```bash
kubectl -n 9router exec hermes-0 -c hermes -- sh -lc 'head -3 /opt/data/config.yaml; test -w /opt/data/config.yaml && echo writable'
```

Hermes can reach 9Router over cluster DNS with its key:

```bash
kubectl -n 9router exec hermes-0 -c hermes -- sh -lc 'curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $OPENAI_API_KEY" http://ninerouter:8080/v1/models'
```

The real round-trip — Hermes → 9Router → provider:

```bash
kubectl -n 9router exec hermes-0 -c hermes -- sh -lc '/opt/hermes/.venv/bin/hermes -z "Reply with exactly: ok"'
```

`ok` means the whole chain works. Add `-c hermes` to any `exec`, or kubectl warns about defaulting past the
init container.

Free models are the `oc/…` ids (`oc/mimo-v2.5-free`, `oc/deepseek-v4-flash-free`); the `opencode-go/…` ids are
a different, non-free provider. Individual free models do go down — a `503 Upstream request failed` is the
provider, not your config. List what is available:

```bash
kubectl -n 9router exec ninerouter-0 -- node -e "fetch('http://127.0.0.1:8080/v1/models').then(r=>r.json()).then(j=>console.log(j.data.map(m=>m.id).filter(i=>i.startsWith('oc/')).join('\n')))"
```

## 🧨 Teardown

```bash
kubectl delete -k .
```

That leaves the PVCs (and therefore both databases). To remove everything including data:

```bash
kubectl delete namespace 9router
```
